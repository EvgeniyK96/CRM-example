# CRM кондитерской фабрики — сценарий и план

Учебный проект (не для продакшена). Стек: Django 5 + DRF + djoser/JWT (бэкенд, на базе шаблона), React SPA + Vite + TypeScript (фронтенд), SQLite → PostgreSQL.

## 1. Роли

| Роль (код) | Доступ |
|---|---|
| `admin` | Всё, пользователи и роли, справочники |
| `sales` — менеджер по продажам | Клиенты, заказы, отгрузки (просмотр) |
| `hr` — отдел кадров | Сотрудники, должности, цеха, табель, отпуска и больничные |
| `accountant` — бухгалтерия | План счетов, проводки, счета и оплаты, расчёт зарплаты, отчёты |
| `technologist` — технолог | Номенклатура, рецептуры (версии) |
| `shop_head` — начальник цеха | Производственные задания своего цеха, запуск и завершение, брак |
| `storekeeper` — кладовщик | Приход сырья, остатки, закупки, отгрузка |

## 2. Предметная область

Цеха: торты и пирожные, пряничный, вафельный, сдобный.
Клиенты: оптовые покупатели, магазины, фирменные магазины.
Заказ клиента → система проверяет остатки готовой продукции → дефицит превращается в производственные задания по цехам → запуск списывает сырьё по рецептуре (FEFO) → выпуск создаёт партию готовой продукции со сроком годности → отгрузка (FEFO) → счёт и оплата.

### Статусы
- Заказ: `new` → `confirmed` → `in_production` → `ready` → `shipped` (+ `cancelled`).
- Задание: `planned` → `in_progress` → `done` (+ `cancelled`).
- Оплата: `unpaid` / `partial` / `paid`.

### Сквозной сценарий
1. Менеджер создаёт заказ магазина (200 пряников, 50 тортов), подтверждает.
2. Система создаёт задания в пряничный и тортовый цеха на недостающее количество.
3. Начальник цеха запускает задание. Сырьё списывается по рецептуре по FEFO. Если не хватает, запуск блокируется и создаётся заявка на закупку.
4. Завершение: фактический выход и брак → партия готовой продукции, привязанная к партиям сырья (прослеживаемость).
5. Все задания выполнены → заказ `ready`. Кладовщик оформляет отгрузку.
6. Бухгалтерия: счёт, оплата, автоматические проводки; себестоимость партии.
7. Конец месяца: табель → расчёт зарплаты → проводки → ведомость.

## 3. Модули и сущности

### accounts
Кастомный `User` (роль), JWT через djoser, права по ролям.

### hr — отдел кадров
Цеха/подразделения, должности, сотрудники (ФИО, дата рождения, ИИН/ИНН, контакты, дата приёма/увольнения, статус), кадровые приказы (приём, перевод, увольнение), трудовые договоры (оклад или сдельная ставка), табель (дни/часы), отпуска, больничные, командировки.

### accounting — бухгалтерия
- План счетов, журнал проводок (двойная запись), контрагенты (из клиентов и поставщиков).
- Автопроводки из бизнес-событий: приход сырья, списание в производство, выпуск продукции, отгрузка (выручка и себестоимость), оплата.
- Зарплата: начисления (оклад, сдельная, премии, отпускные, больничные), удержания (налоги и взносы со **ставками в настройках**, т.к. учебная упрощённая модель), расчётный листок, ведомость, выплата.
- Отчёты: оборотно-сальдовая ведомость, карточка счёта, расчётная ведомость, дебиторка.

### catalog
Единицы измерения, категории, номенклатура (сырьё, готовая продукция), поставщики.

### recipes
Рецептуры с версиями (выход партии, строки сырья, потери).

### warehouse
Партии (сырьё и продукция) со сроками годности, складские движения (приход, расход, выпуск, отгрузка, брак), остаток = сумма движений, FEFO.

### purchasing
Заявка поставщику, приёмка → партии сырья.

### sales
Клиенты (тип, адреса, условия оплаты), заказы и строки, отгрузки.

### production
Производственные задания, запуск (списание), завершение (выпуск), брак, прослеживаемость.

### reports
Дашборд: загрузка цехов, остатки ниже минимума, истекающие сроки, выручка, брак, прослеживаемость партии.

### Демо-данные
`python manage.py seed_demo` — всё сразу: пользователи всех ролей (пароль `demo12345`), цеха и должности,
каталог (25 видов сырья, 9 продуктов, 5 поставщиков), активные рецептуры, начальные остатки сырья
через проведённые приёмки (есть просроченные и истекающие партии), отправленная заявка поставщику,
7 клиентов, начальные остатки готовой продукции, 4 заказа в разных статусах и производственные задания
(выполненное, в работе, запланированные), отгрузка готовых заказов. Начальники цехов: `shop_cakes` (торты), `shop_ginger` (пряники);
`shop_head` — начальник производства, видит все цеха.
Команды идемпотентны; по отдельности: `seed_hr`, `seed_catalog`, `seed_recipes`, `seed_purchasing`, `seed_sales`, `seed_production`, `seed_shipping`, `seed_accounting`, `seed_payroll`.
`python manage.py accounting_backfill` — проводки для операций, проведённых до появления бухгалтерии (повторный запуск безопасен).

### Архитектурные соглашения
- Бизнес-логика — в `services.py` приложений; вьюхи только вызывают сервисы.
- Ошибки бизнес-правил — наследники `core.exceptions.DomainError`, API отвечает 400 `{"detail": ...}`.
- Документы со строками — `core.serializers.LinesWriteMixin`; редактируется только черновик (`is_editable`).
- Остатки — только через `apps.warehouse.services` (`receive`, `consume_fefo`, `write_off`); остаток = сумма движений.
- Резерв готовой продукции — `reserved_qty` в строках открытых заказов, не движение по складу;
  свободно = годное на дату отгрузки − резервы других заказов. Недостающее — `to_produce` (основа для этапа 5).
- Производство: задание фиксирует версию рецептуры; распределения (`TaskAllocation`) связывают задание со строками
  заказов; выпуск переводит количество из `to_produce` в `reserved_qty`. Списания сырья (`TaskConsumption`)
  дают прослеживаемость «продукция ← сырьё ← поставщик».
- Начальник цеха, привязанный к производственному цеху через карточку сотрудника, управляет только его заданиями.
- Отгрузка (`Shipment`) — только целиком готового заказа; партии списываются по FEFO, `ShipmentItem` хранит
  «партия → строка заказа». Выручка = Σ кол-во × цена заказа, себестоимость = Σ кол-во × себестоимость партии.
- Все `Decimal` в API — строки (`core.renderers.JSONRenderer`), в том числе в ответах-словарях без сериализатора.
- Бухгалтерия подписана на сигналы доменных модулей (`*/signals.py` → `accounting/receivers.py`) и пишет проводки
  в той же транзакции: доменные модули о бухгалтерии не знают, а ошибка проводки откатывает операцию.
  Одно основание — одна операция (`unique(source_type, source_id)`), поэтому обработчики идемпотентны.
- План счетов упрощён по образцу типового плана РК (без НДС, без субсчетов); коды — данные (миграция), автопроводки
  ссылаются на них через `accounting/chart.py`. Брак при выпуске включается в себестоимость годной продукции.
- Кадры: отдел, должность, оклад и увольнение меняются только кадровыми приказами (история «было → стало»);
  при увольнении учётная запись блокируется. Табель строится из календаря (`Holiday`) и отсутствий.
- Зарплата — учебная модель по образцу РК: ставки в таблице `PayrollRate` (правит бухгалтер), стандартный вычет
  и среднее число дней месяца — в настройках (`PAYROLL_STANDARD_DEDUCTION`, `PAYROLL_AVG_MONTH_DAYS`).
  Зарплата — расходы периода (директ-костинг): цеха → 7110, остальные → 7210; себестоимость продукции — сырьевая.
- Отчёты (`apps/reports`) только читают данные; разделы дашборда отдаются по ролям (`SECTIONS`), чужие разделы
  не попадают в ответ. Графики — recharts с проверенной палитрой (`frontend/src/components/charts/theme.ts`),
  у каждого графика есть табличный вид; таблицы отчётов выгружаются в CSV (BOM, «;», десятичная запятая — для Excel).

## 6. Допущения
- Налоги и взносы зарплаты упрощены и задаются в настройках (не юридически точный расчёт).
- SQLite для разработки, PostgreSQL через `DATABASE_URL`.
- Складские остатки считаются из движений; операции атомарны (`transaction.atomic`, `select_for_update`).
